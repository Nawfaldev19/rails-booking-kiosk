# Deploying a free live demo (Render)

This is a checklist for putting the demo online on Render's free tier. [`render.yaml`](render.yaml) describes everything; nothing is deployed until you connect the repository.

What you get: a Rails API (`booking-kiosk-api`), a Postgres database (`booking-kiosk-db`), the member app (`booking-kiosk-member`) and the kiosk (`booking-kiosk-desk`).

Why two static sites rewrite `/graphql`: the apps call `/graphql` on their own origin so the session cookie stays first-party and no CORS is needed ([ADR 0007](docs/adr/0007-same-origin-clients-cookie-sessions-and-strict-headers.md)). Vite's proxy does that in development; on Render each static site rewrites `/graphql` to the API.

Free-tier behaviour to expect:

- The API sleeps after about 15 minutes idle; the first request afterwards takes up to a minute.
- Render's free Postgres expires after 30 days. Recreate it (the app reseeds an empty database on start) or move to a paid plan.
- No scheduler runs. Holds still expire exactly (they are checked on read), but failed outbox messages are not retried. That only matters for invitation mail.
- Mail is not sent (`MAIL_DELIVERY=file`). Invitations are written to the API's disk, so the invitation flow cannot be completed by a visitor.

## Steps

1. Create a Render account at render.com (sign in with GitHub) and grant it access to this repository.
2. Push the repository to GitHub.
3. In Render choose **New > Blueprint**, pick this repository, and apply. Render creates the database, the API and both sites.
4. If Render added a suffix to any site name (the name was taken), the hostnames in `render.yaml` are wrong. Fix these, then redeploy:
   - on both static sites, the `/graphql` rewrite destination (the API host);
   - on the API, `ALLOWED_ORIGINS` (both site origins, comma-separated, no trailing slash), `MEMBER_APP_URL` and `APP_HOST`.
5. Check `https://<api-host>/up` returns 200, then open the member site and sign in with one of the one-click demo buttons.
6. Check that the session cookie is set and a booking can be held. If the rewrite does not forward `/graphql` or the cookie, that is the part to debug first: Render's rewrite rules are what replace Vite's proxy. If it does not work, the fallback is to serve both apps from one reverse proxy.
7. Put the two URLs in the "Live demo" line of the README.

## Environment variables

| Service | Variable | Value |
|---|---|---|
| API | `RAILS_ENV` | `production` (blueprint) |
| API | `DATABASE_URL` | from `booking-kiosk-db` (blueprint) |
| API | `SECRET_KEY_BASE` | generated by Render (blueprint) |
| API | `MAIL_DELIVERY` | `file` (no SMTP on the demo); set `SMTP_ADDRESS` and friends instead for real mail |
| API | `ALLOWED_ORIGINS` | the member and kiosk site origins |
| API | `MEMBER_APP_URL`, `APP_HOST` | the member site origin and host, used in invitation links |
| Sites | `NODE_VERSION` | `22.12.0` (blueprint) |

Demo accounts and the password are in the README quick start.
