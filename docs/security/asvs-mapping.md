# OWASP ASVS 5.0.0 mapping

A chapter-level self-assessment against the [OWASP Application Security Verification Standard 5.0.0](https://owasp.org/www-project-application-security-verification-standard/). It is aligned with ASVS, not certified; individual requirement IDs are not cited. Tests per control: [traceability.md](../testing/traceability.md#security-controls--tests).

| Chapter | Applies | Controls | Verified by | Gaps |
|---|---|---|---|---|
| V1 Encoding and Sanitization | Yes | React escapes output; message bodies are plain text; Liquid with an allow-list; SQL only with bound parameters | [`messages_spec.rb`](../../api/spec/messages/messages_spec.rb), SQL-shaped input in [`tenant_isolation_spec.rb`](../../api/spec/requests/tenant_isolation_spec.rb) | None known |
| V2 Validation and Business Logic | Yes | Model validations; `SlotRules`; hold limit under a record lock; template length bounds and a linear-time range check; database constraints as the last line | [`bookings_spec.rb`](../../api/spec/services/bookings_spec.rb), [`concurrency_spec.rb`](../../api/spec/services/concurrency_spec.rb), [`constraints_spec.rb`](../../api/spec/db/constraints_spec.rb) | No general request-rate limit |
| V3 Web Frontend Security | Yes | Strict Content Security Policy without `'unsafe-inline'` and the other headers in [ADR 0007](../adr/0007-same-origin-clients-cookie-sessions-and-strict-headers.md); HTTP-only cookies; no credentials in storage | [`security-headers.spec.ts`](../../web/e2e/security-headers.spec.ts) | A production proxy must send the same headers |
| V4 API and Web Service | Yes | JSON-only endpoint, origin allow-list; limits on query length, tokens, depth, complexity and page size; introspection off in production; typed errors without internals; `no-store` | [`auth_and_transport_spec.rb`](../../api/spec/requests/auth_and_transport_spec.rb), [`security_headers_spec.rb`](../../api/spec/requests/security_headers_spec.rb) | None known |
| V5 File Handling | N/A | No uploads and no user files | — | — |
| V6 Authentication | Yes | bcrypt, 10–72 characters within 72 bytes; constant-time `authenticate_by`; failed attempts limited per account and per client address, with the address taken from `X-Forwarded-For` only behind trusted proxies; invitations instead of manager-set passwords; password change with the current password | [`auth_and_transport_spec.rb`](../../api/spec/requests/auth_and_transport_spec.rb), [`team_spec.rb`](../../api/spec/requests/team_spec.rb) | No MFA, password reset or breached-password check |
| V7 Session Management | Yes | Encrypted HTTP-only `SameSite=Lax` cookie, `Secure` in production; reset on sign-in and sign-out; 2-hour idle and 12-hour absolute expiry; all sessions end on a password change | [`auth_and_transport_spec.rb`](../../api/spec/requests/auth_and_transport_spec.rb), [`team_spec.rb`](../../api/spec/requests/team_spec.rb) | No per-session revocation |
| V8 Authorization | Yes | One role table; `tenant.authorize!` in every service and resolver; data only through `Tenant`; composite keys; managers can remove or demote people, never themselves | [`tenant_isolation_spec.rb`](../../api/spec/requests/tenant_isolation_spec.rb), [`team_spec.rb`](../../api/spec/requests/team_spec.rb) | Reads are not isolated by the database ([ADR 0003](../adr/0003-tenant-isolation-through-a-scoped-access-object-and-composite-keys.md)) |
| V9 Self-contained Tokens | Partly | Session tokens from `generates_token_for` are signed by Rails and carry their own expiry, inside an encrypted cookie; invitation tokens are random and stored as digests | [`auth_and_transport_spec.rb`](../../api/spec/requests/auth_and_transport_spec.rb) | Key rotation is the deployer's job |
| V10 OAuth and OIDC | N/A | No OAuth or OpenID Connect | — | — |
| V11 Cryptography | Partly | bcrypt; SHA-256 digests of 256-bit random invitation tokens; Rails' encrypted cookies keyed by `SECRET_KEY_BASE`; no custom cryptography | [`team_spec.rb`](../../api/spec/requests/team_spec.rb) | Key management is the deployer's job |
| V12 Secure Communication | Partly | `force_ssl` and `assume_ssl` in production | — | TLS termination is outside this repository |
| V13 Configuration | Yes | Settings from the environment ([configuration.md](../reference/configuration.md)); no secrets committed; mail delivery must be chosen explicitly in production; dependencies locked and audited; CI actions pinned | [`ci.yml`](../../.github/workflows/ci.yml), [supply-chain.md](supply-chain.md) | Docker Compose uses development defaults |
| V14 Data Protection | Yes | Members shown by name only; emails visible to the person and to managers for their staff and outbox; `no-store`; passwords, emails, tokens and GraphQL variables filtered from logs | [`auth_and_transport_spec.rb`](../../api/spec/requests/auth_and_transport_spec.rb), [`workspace_api_spec.rb`](../../api/spec/requests/workspace_api_spec.rb) | No retention or deletion policy |
| V15 Secure Coding and Architecture | Yes | Database-enforced invariants; thin resolvers; one validation place per concern; permissive, locked dependencies; lint, types, Knip and coverage floors in the gate; Brakeman run ad hoc (0 warnings, [how-to](../how-to/run-the-tests.md#optional-brakeman)) | `make verify` | Code analysis through GitHub's CodeQL default setup, not a workflow file |
| V16 Security Logging and Error Handling | Yes | One structured log line per operation; delivery failures logged with the error class; generic error responses | log-filter spec in [`auth_and_transport_spec.rb`](../../api/spec/requests/auth_and_transport_spec.rb) | No alerting or log retention |
| V17 WebRTC | N/A | Not used | — | — |
